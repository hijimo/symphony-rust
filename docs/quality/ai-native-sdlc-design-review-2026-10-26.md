## 阻断问题

### A1. 平台独立 `CODEX_HOME` 里没有 Codex 认证，工作台和起草 agent 无法调用模型

- **问题**：工作台方案 4.2 和 codex-org-config 第 3 节规定第一期 `CODEX_HOME` 指向平台管理的独立目录，“只放最小 `config.toml`”。Codex 的登录凭据（`auth.json`）也放在 `CODEX_HOME` 下，独立目录里没有它，Codex 会处于未登录状态。
- **依据（已核实）**：`web-platform/src/process_manager/spawn.rs` 的环境变量白名单包含 `CODEX_HOME`，现有编排器的 Codex 依赖部署环境里的这个目录完成认证；本地 `~/.codex/` 下也有 `auth.json`。
- **建议**：方案写明平台 `CODEX_HOME` 的认证来源，二选一：
  1. 部署时由运维把认证文件放进平台目录（与编排器共用同一份凭据）；
  2. 在平台 `config.toml` 中配置模型 provider，通过环境变量读取 API key，并把该变量加入白名单。
  同时写明：认证文件不进入任何 Git 仓库，也不暴露给工作区内执行的命令。

### A2. 多仓库路径布局在两份方案中不一致，且 `repos/` 嵌在主仓库内会冲突

- **问题**：
  - 工作台方案 4.1：主仓库检出在工作区根目录，从仓库放在主仓库内部的 `repos/<alias>/`。
  - 流程方案第 5、7 节：`## Files` 路径前缀“与实现阶段多仓库工作区的目录布局一致”。
  - 实现阶段的多仓库布局是 `<ws>/<alias>/`，**主仓库也在别名目录下**。
  - 结果：同一个后端文件，在工作台里是 `repos/backend/...`，在 plan 里要写成 `backend/...`，偏离检测会对不上；单仓库项目和多仓库项目的主仓库前缀规则也不同。
  - 另外，主仓库本身如果已有 `repos/` 目录，会和检出目录冲突。
- **依据（已核实）**：`docs/方案/multi-repo-workspace-design.md` 第 83、362 行（“即使只配了 primary 一项，仓库也在 `<ws>/<alias>/` 下”）。
- **建议**：工作台工作区采用与实现阶段相同的布局。多仓库项目：工作区根目录不是仓库，主仓库和从仓库都在 `<ws>/<alias>/` 下；单仓库项目：主仓库在根目录，不加前缀。`writablePaths` 相应改为 `<primary-alias>/.symphony/changes/<iid>/**`。`## Files` 的前缀规则写成一句：与实现阶段工作区的相对路径完全相同。

### A3. 文档阶段没有入口和监听机制，人工改 label 时会和编排器竞争

- **问题**：
  1. 默认路径是 `track:plan`，但没写由谁发现“新 Issue 需要起草 plan”。web-platform 现在不轮询 Issue，只有 rust-platform 轮询，而编排器又规定不处理 `doc:*`。在 GitLab / GitHub 上直接创建的 Issue 不会进入文档流程。
  2. 流程方案 4.1 规定“文档阶段的 label 被人手动修改时，web-platform 按数据库改回”，同样需要 web-platform 监听 label 变化，这个能力不存在。
  3. 如果有人把文档阶段的 Issue 手动改成 `Todo`，编排器会在 web-platform 改回之前开始实现，两边竞争。
- **依据（已核实）**：`rust-platform/src/tracker/gitlab.rs` 的 `fetch_candidate_issues` 只按 `active_states` 过滤；web-platform 的看板接口只在用户打开页面时查询。
- **建议**：
  - 文档流程只从 Symphony 界面进入：“新建需求”，或在 Issue 卡片上点“开始文档流程”。平台上直接创建、没有路径 label 的 Issue 停在“计划”列的“待启动”，不自动起草。`track:plan` 的“默认”含义改为：在 Symphony 界面启动文档流程时默认选中 `plan`。
  - 删除“web-platform 自动改回 label”的规则。人手动改 label 视为人工覆盖：web-platform 下次读取时发现不一致，在卡片上提示“label 与文档状态不一致”，不自动改回。
  - 与已确定的 M4 一致：手动打 `Todo` 的 Issue 按 `track:fast` 处理。

### A4. 状态推导规则与“合并失败不推进”互相矛盾

- **问题**：流程方案 4.5 写“`plan = approved` → Todo”；第 10.2 节第 5 步写“合并成功才进入 Todo，合并失败时 Issue 停在 `doc:plan-review`”。按 4.5 实现，G3 一批准就会写 `Todo`，编排器会从**还没有文档的主干**切分支开始实现。
- **建议**：4.5 改为：
  - `plan = approved` 且文档 MR 未合并 → `Plan Review`（子状态“已批准，待合并”）；
  - 文档 MR 已合并（三份文档进入 merged）→ `Todo`。

### A5. 文档目录 `.symphony/` 与运行时私有目录约定冲突

- **问题**：现有代码和方案把 `.symphony/` 当作**不提交的运行时私有目录**：rust-platform 在工作区下用 `.symphony/tmp`、`locks`、`quarantine`、`askpass`；teamwork 方案规定 `.git/info/exclude` 写入 `.symphony/`，并使用 `.symphony/handback.md`。单仓库项目的实现工作区就是仓库检出本身，按 teamwork 方案排除 `.symphony/` 后，实现 agent 对 `.symphony/changes/<iid>/plan.md` 的修订**不会被提交**。
- **依据（已核实）**：`rust-platform/src/workspace/mod.rs`、`repos.rs`、`gc.rs`、`agent/runner.rs` 中的 `.join(".symphony")`；`rust-platform/src/config/repos.rs` 把 `.symphony` 列为保留别名；`docs/方案/teamwork-integration-scheme.md` 第 81、424 行。
- **建议**：文档目录改名，与运行时目录分开，例如 `symphony-changes/<iid>/` 或 `docs/changes/<iid>/`。不建议用 exclude 例外规则（`!.symphony/changes/`）绕过，容易在以后的改动中再次被排除。

## 重要问题

### B1. 非交互模式下，需要审批的命令没人应答

- **问题**：工作台方案 4.2 规定“其他命令按 `agentPolicy` 处理”，交互模式下由人点击允许或拒绝。非交互起草时没有人在线，审批请求会一直挂起，直到触发卡死检测。
- **建议**：非交互模式下，只读命令自动允许，其他命令一律自动拒绝，并告诉 AI 原因。写进工作台方案 4.2 和流程方案 4.7。

### B2. 非交互起草和人工交互共用一个会话，会同时操作

- **问题**：工作台方案规定两种模式共用同一个阶段会话。AI 自动起草 spec 时，有人打开工作台发消息，会在同一会话上并发发起新一轮。
- **建议**：同一会话同一时间只允许一轮。非交互起草期间，工作台显示“AI 正在起草”，输入框禁用，或者把消息排队到本轮结束后再发送。

### B3. 打回后 AI 重新起草，可能覆盖人的修改

- **问题**：流程方案 4.5 规定 `changes_requested` 回到起草状态，“意见作为下一轮 agent 输入”。没写 AI 是在现有文档上修改，还是从模板重写。审阅人可能已经在工作台里直接改过部分内容。
- **建议**：打回后 AI 在**当前文档**上按意见修改，不从模板重写；修改结果同样以 diff 呈现，可以逐块接受或回退。

### B4. 退回 r2 的细节不完整

- **问题**：流程方案第 10.2 节第 17 步：
  1. “复制当前文档”没说是主干上已合并的版本，还是实现分支上带“实现期修订”的版本；
  2. 已经打开的代码 MR 怎么处理没写；
  3. r2 合入主干后，实现分支 merge 新主干时，自己对 plan.md 的修订会和 r2 的改动冲突。
- **建议**：以**实现分支上的最新版本**为准复制到 r2（包含实现期修订）；代码 MR 保持打开并转为 Draft，回到实现阶段后继续使用；r2 合并后，实现分支 merge 主干时，plan.md 冲突一律以主干（r2 已批准版本）为准。

### B5. “每次保存即 commit / push”频率过高

- **问题**：工作台方案第 7 节写“每次保存即在文档分支 commit / push”。编辑器自动保存很频繁，每次 push 都会触发平台事件和 CI，也会让文档分支历史很乱。
- **建议**：自动保存只写工作区文件；以下时机才 commit 并 push：用户点“保存”、AI 一轮结束、提交审阅、批准前。

### B6. 流程方案 P1 依赖工作台 M1–M3，分期没有写明

- **问题**：流程方案 P1 的自动起草、审阅中让 AI 修改，依赖工作台方案的 M1–M3（工作区、编辑、AI 会话）。两份方案的分期没有对应关系，排期时容易只做一边。
- **建议**：流程方案第 12 节写明：P1 前置条件是工作台 M1–M3 完成；M4（体验打磨）可以与 P1 并行。

### B7. 写入的 label 名称要和项目实际使用的状态名一致

- **问题**：web-platform 在交接时把 `doc:plan-review` 换成 `Todo`。现有代码里存在两种命名：模板里用 `Todo`、`In Progress`，平台状态机测试里用 `workflow::todo` 这类映射。写错名字，编排器就识别不到。
- **依据（已核实）**：`rust-platform/src/platform/workflow.rs` 按 `config.workflow.states` 映射 label；`web-platform/src/templates/workflow_*.md` 的 `active_states`。
- **建议**：写明交接时写入的 label 取自该项目 WORKFLOW 配置中 Todo 状态对应的 label 名，不写死字符串。

### B8. AI 写入自动批准后，提示注入可以通过 plan.md 传到实现阶段

- **问题（推断）**：AI 能读完整仓库和从仓库，写入白名单内自动批准。仓库内容里如果有恶意指令，可能被写进 plan.md；实现阶段的 agent 把 plan.md 当作必须遵循的计划，并且带着平台 Token 运行。
- **建议**：写明 G3 是这条链路的唯一人工防线，审阅清单增加一项“plan 中是否有与需求无关的操作（如外部网络访问、修改 CI、读取凭据）”；实现阶段提示词说明 plan.md 只描述改动范围，不能覆盖 WORKFLOW 中的安全规则。
